Sales Documents · UX Review

Quotations and invoices are functionally solid and visually improvised.

A review of the creation, printing, and listing flow for Quotations and Invoices — the two document types every other module (Expenses, POS, Purchases) will inherit patterns from. Findings are pulled directly from the current codebase, not general ERP advice.

The underlying business logic is careful — totals recompute correctly, permissions are enforced, the ZATCA pipeline genuinely signs and clears real invoices. But four independent status-badge systems disagree with each other, an invoice can print successfully while silently failing to save, and a printed QR code can claim “VERIFIED ORIGINAL” on an invoice ZATCA never cleared. None of this is one team's mistake — it's the accumulation of features built one at a time without a shared vocabulary to build them in.

This review is organized in the order a stakeholder should read it: what's actually broken and worth fixing first (§01), why it keeps recurring (§02), the shared system proposed to fix it (§03), and two concrete exhibits showing that system applied to the invoice creation flow and the Sales Invoices list (§04–05). §06 is a phased recommendation. Nothing here has been built yet — this is the proposal.

01 / Findings — ranked by what a customer or auditor would actually notice

Trust & correctness gaps

These aren't polish items. Each one makes the application say something to a user, or to ZATCA, that isn't true.

A printed QR code can claim clearance that never happenedCritical

When an invoice has no real ZATCA-issued QR payload yet, the printed document falls back to a placeholder string that still reads Status: VERIFIED ORIGINAL — regardless of whether the invoice's actual zatcaStatus is NOT_SUBMITTED, ERROR, or REJECTED. A customer scanning that code gets nonsense data next to a claim of official verification.

DocumentRenderer.tsx — QR fallback, ~L393
An invoice can appear to save successfully and not actually saveCritical

Invoice creation writes to local state, opens the print preview, and shows success — before a fire-and-forget background sync to Postgres has even resolved. If that sync fails, the only signal is an unrelated global connection banner elsewhere in the app. Quotations don't have this problem: they await a real save request and surface the server's actual error.

InvoiceModule.tsx handleSaveInvoice ~L238–306 · App.tsx handleUpdateDb ~L214–236
A ZATCA rejection is invisible to the person who needs to see itHigh

Every invoice auto-submits to ZATCA in the background on save. Failure is caught and sent to console.error only — no toast, no badge change, nothing on screen. The status only becomes visible if someone later opens the invoice and happens to check.

InvoiceModule.tsx ~L293–302 · QuotationModule.tsx conversion path ~L429–438
“Showing X of Y records” can understate the real countHigh

Invoice and quotation lists are capped server-side at 500 rows. The pagination footer's “of Y” reads that capped count as if it were the whole company's history — a business with 600 invoices sees a list that looks complete and isn't, with no signal that anything is missing.

server/lib/pagination.ts · InvoiceModule.tsx ~L818–862

These four earn a fix before anything cosmetic. A design system can't build trust on top of a QR code that lies.

02 / Root cause

A fragmented system, not a fragmented team

Status is the single most important thing either document communicates — cleared or rejected, paid or owed, draft or issued. It's currently drawn five separate ways, each hand-built in its own file, none aware the others exist:

Invoice status (own palette) Payment status (reuses indigo) ZATCA status (outline style, not filled) Quotation status (cyan appears nowhere else) Print-view status (a 5th, narrower re-implementation)

Indigo means “primary action” on every button in the app, and separately means “partially paid” on the invoice list. Cyan means “converted” on the quotation list and means nothing anywhere else. The printed document collapses Draft and Sent into the same grey, even though the list distinguishes them. None of this is arbitrary bad taste — each badge was built correctly, in isolation, by someone solving one screen at a time. What's missing is a shared answer to “what does this color mean,” owned once.

The same pattern repeats structurally: the invoice list and quotation list each hand-roll their own table, their own sort logic, their own pagination bar — nearly identical, independently maintained, already drifting (only Invoices has filters; only Invoices shows a bank column; the two fetch their data on entirely different refresh models). Every module built after these two will either copy the drift forward or need this fixed first.

03 / The proposal

One system, three roles, five meanings — used everywhere after this

This is the shared vocabulary every list, badge, and printed document should draw from. It doesn't reinvent the app's existing visual language — slate neutrals, rounded cards, a confident accent — it gives that language a single source of truth instead of five.

Status pill — one component, five states, used everywhere

Same shape, same sizing, same dot-plus-label pattern for invoice status, payment status, and ZATCA status alike. The dot alone should be legible at a glance without reading the label — the current 9px text asks too much of a quick scan.

04 / Exhibit A

What changed and why:

  • Search box — today, finding one customer's invoice among hundreds means sorting by column and scanning by eye. This is table stakes for any list past a few dozen rows.
  • Type column replaces guessing from the invoice number format — B2B/B2C is a real ZATCA distinction the user should see without opening the record.
  • Actions appear on hover/focus instead of always rendering three to five buttons per row, which wraps unpredictably on medium screens today.
  • “Showing 1–4 of 4” — this footer text should always reflect a true count. If the backend's 500-row cap is ever hit, the label changes to Showing 1–20 of 500+ — refine your search to see more instead of implying completeness it can't back up.
  • Freshness indicator — makes the current Invoices-vs-Quotations data-staleness asymmetry a visible, honest state instead of a silent inconsistency between the two lists.

06 / Recommendation

Phased, not all-at-once

This is deliberately staged so trust issues land first, the shared system lands second as a foundation, and visual polish lands last — on top of a system every future module (Expenses, POS, Purchases) can reuse instead of re-deriving.

PhaseShipsWhy this order
P0Fix the QR “verified” fallback, make invoice save await-and-confirm, surface ZATCA failure in the UI, make the record count honest.Correctness bugs, not design debt — each one actively misleads someone today.
P1Ship the shared StatusPill, DataTable, and Pagination components; migrate both list views onto them.Everything after this reuses these three components instead of copy-pasting a fourth table.
P2Unify quantity precision, payment-status options, and the save/print flow shown in §04 across both modules.Removes the remaining Quotation-vs-Invoice asymmetries once the shared components exist to enforce consistency.
P3Search, saved filters, and the redesigned list from §05 as the new default.Pure UX upside, safest to ship last since nothing downstream depends on it.

Waiting on a decision here.

P0 can start immediately — none of it depends on approving the design system. P1 onward is the point of no return in a good way: once StatusPill, DataTable, and Pagination exist, every module after Quotations and Invoices — Expenses, POS, Purchases — should be built on top of them rather than repeating the pattern this review is here to fix.
