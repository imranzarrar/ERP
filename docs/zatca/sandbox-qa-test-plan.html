QA Test Plan · ZATCA Sandbox

Proving the sandbox pipeline holds — for every company, every invoice shape.

This plan tests three things at once, because they're only meaningful together: the onboarding wizard's UX and state machine, the automatic ZATCA-sample-key adoption that now makes every new sandbox company signature-valid, and the invoice generation pipeline across the full B2B/B2C scenario space — each case checked against both ZATCA's real API and the SDK's independent local validator before it counts as passed.

Key decision this plan is built on

Sandbox now automatically adopts ZATCA's own published sample private key whenever their sandbox returns its known static Production CSID certificate — which it always does, for every company, because every sandbox company shares the same ZATCA-documented test VAT (399999999900003). This requires no manual step per company — it fires inside request-production-csid the moment the known certificate comes back. Simulation/Production never trigger it; they use each company's own real, unique VAT and keep the strict key/certificate match requirement exactly as before. This plan verifies that promise holds across multiple companies, not just the one it was discovered on.

Three things must all be true before this sandbox pipeline is trustworthy enough to justify moving to Simulation: the wizard takes a brand-new company from nothing to a working signature with no manual cryptographic intervention; every invoice shape ZATCA's schema actually allows (single/multi-line, discounted, mixed tax rates, 20+ lines) produces XML that clears two independent checks, not one; and the Sales Invoices list always shows what actually happened, not what the wizard assumed would happen.

01 / Test environment

What has to exist before testing starts

  • ≥3 test companies, created fresh through the real company-creation flow (not reused from prior sessions) — see §07 for why one company is never enough evidence.
  • Each company needs: one bank account, at least one tax slab per rate under test (15% standard, 5% reduced, 0% exempt — all three already exist as shared slabs), an open fiscal month covering the test date, ≥2 customers per company (one B2B with full ZATCA identity, one B2C with name only).
  • JDK 11 + the ZATCA SDK jar, already installed and kept specifically for this recurring verification need — fatoora -validate and fatoora -generateHash are the independent oracle for every test case, not optional tooling.
  • Dev server restarted before each test pass (no hot-reload on server-side changes in this project) — re-confirmed the hard way in item 35 (BACKLOG.md), where a full session of server-side edits sat inert against an already-running process until this was caught by a test result contradicting the source.
  • New precondition since item 35 (BACKLOG.md): every test company now needs companies.zatcaEnabled = true before Gate 1 (§03) can fire at all — a company defaults to zatcaEnabled = false on creation, and every invoice on it lands at a DISABLED status with zero ZATCA calls attempted until either Sandbox onboarding completes (auto-enables it) or a Super Admin flips it manually in Admin Settings. A pre-existing test company from before item 35 needs this checked explicitly, not assumed.

05 / Predicted risk area — flagged before testing, not after

Mixed tax rates on one invoice (B2B-06 / B2C-04)

Reading xmlBuilder.ts ahead of writing this plan: the header-level cac:TaxTotal/cac:TaxCategory block is currently built from a single rate — headerVatRate = data.items[0]?.vatRate ?? 15 — one TaxSubtotal, taken from the first line item only. ZATCA's schema expects one TaxSubtotal per distinct tax category actually present on the invoice (this is exactly what rules like BR-CO-17/BR-CO-18 in the EN16931 rule set check). An invoice with a 15% line and a 0% line would, as the code reads today, report only the 15% category at the header level — the 0% line's tax would be silently absent from the breakdown ZATCA is validating against.

This is a prediction, not a confirmed defect — flagging it here so B2B-06/B2C-04 get run first and treated as the most likely real finding of this whole test pass, rather than being discovered by accident deep into a long test session.

Confirmed — this prediction was correct

Verified exactly as predicted: the per-line tax slab selector was decorative — the server ignored it entirely and re-taxed every line at one shared header rate. Fixed with a real invoice_items.tax_slab_id column, per-line rate resolution server-side (processInvoice.ts, transactions.ts), and a genuine multi-TaxSubtotal grouping in xmlBuilder.ts keyed by (category code, rate) instead of one hardcoded block. Verified live on a real mixed-rate invoice (2 lines at 15% standard, 1 line at 0% exempt): the emitted XML carries two distinct cac:TaxSubtotal blocks (S/15%/SAR 60 and E/0%/SAR 0), and ZATCA's real sandbox cleared it. This surfaced one new, legitimate warning (BR-KSA-23, VAT exemption reason code) — tracked, not blocking; see §09.

08 / Field requirements vs. ZATCA's own data dictionary

Checked against the source, not assumed from earlier reasoning

This project's validateBuyerFields logic (B2B requires VAT/address, B2C only requires a name) was built from general ZATCA documentation earlier this session. Before trusting it further, it was checked directly against ZATCA's published Electronic Invoice XML Implementation Standard — the actual per-field Mandatory/Conditional/Optional table, not a summary of it.

FieldStandard (B2B)Simplified (B2C)Matches current code?
Buyer VAT number (BT-48)MandatoryOptionalYes
Buyer nameMandatoryMandatoryYes
Buyer address (street/building/district/city/postal)MandatoryConditionalPartial — see below
One nuance to resolve during testing, not before

ZATCA marks B2C buyer address as Conditional, not flatly Optional — meaning some condition makes it required some of the time. The current code treats it as always-optional for B2C. Add a test case: a B2C customer with a VAT number present but no address, and confirm whether ZATCA's real sandbox accepts it cleanly or flags a conditional-field warning. If it does, the condition needs identifying and the validator needs a small update; if it doesn't, no change needed — but this should be confirmed by evidence, the same way everything else in this plan is, not left as an assumption.

POS / EGS unit scope — decided, not deferred silently

ZATCA's model ties a signing identity to an "EGS" (E-invoice Generation Solution) unit, and its own documentation allows registering a separate EGS unit per physical device for businesses where individual POS terminals sign invoices independently. Checked against this project's actual architecture: every invoice — POS sale or not — is generated and signed server-side, by this one backend, never by an individual terminal in isolation. That makes the whole company's POS estate one EGS unit, which is exactly the current one-CSR-per-company model.

Explicit scope decision (this phase)

No per-POS-terminal device identity, no new onboarding input field for it, this phase. This is scoped to the current architecture — every invoice is signed centrally by the server. Revisit only if the architecture changes — specifically, if any POS terminal is ever built to sign/submit invoices on its own without going through this backend, at which point ZATCA would expect that terminal to have its own EGS unit, CSR, CSID, and OTP, and onboarding would need a real "register a device" step to match.

Remediation loop — a blocking failure does not end the plan

10 / Scope boundary — what changes for Simulation/Production

This plan is Sandbox-only. Here is exactly what's different next.

Nothing in this plan — the sample-key adoption, the shared test VAT, the static Production CSID — applies once a company moves to Simulation or Production. Restating the boundary precisely, since it's the one thing this entire plan must never blur:

  • Simulation/Production each start from a company's real, unique VAT/CR and other mandatory fields — entered once, genuinely, not the shared sandbox placeholder.
  • The OTP for those environments comes from a real login to ZATCA's Fatoora portal, is valid for roughly one hour, and is used exactly once, inline, to exchange a freshly generated CSR for a Compliance CSID — never persisted.
  • The ECDSA key pair and CSR are generated fresh, locally, per company per environment — exactly as sandbox does today, except the certificate ZATCA returns will genuinely, cryptographically match that key, because there is no shared identity for ZATCA's backend to collide against.
  • The resulting Compliance CSID, then Production CSID — certificate, secret, and the private key itself — are saved as part of onboarding, in the same per-environment storage this app already uses (zatcaEnvironmentConfigs), and from that point on every real invoice is signed and stamped with exactly that saved key/certificate pair automatically. No sandbox shortcut, no manual re-entry per invoice.
  • The key/certificate mismatch guard built during this session's investigation stays fully strict for these two environments — if ZATCA ever returned a non-matching certificate here, it would still be rejected outright, exactly as before the sandbox-specific exception existed.

In short: sandbox's fixed-key behavior is a documented accommodation for ZATCA's own shared test data, confirmed by ZATCA's own developer forum, and is applied nowhere outside sandbox. Simulation and Production onboard exactly the way the wizard already describes — real OTP, real company details, a real per-company key/certificate pair, saved once and reused for every invoice after.

Exit criteria

  • All matrix cases actually run (§04, §12) pass both gates on Company 1 — zero errorMessages, zero blocking SDK failures.
  • Companies 2 and 3 (§07) reach onboarding + a real invoice pass with zero manual cryptographic intervention.
  • B2B-06/B2C-04 (mixed tax rates) result is known — confirmed as a real defect and fixed before sign-off (§05).
  • Every onboarding UX checkpoint in §02 behaves exactly as specified, including the sandbox-specific Production CSID message and both guard checks (environment-activation, invalid-VAT-blocks-CSR).
  • Invoice list (§06) never shows a status the database disagrees with, across all three companies — DB-level confirmed; visual List UI unverified this pass (environment limitation, see §06/§12).

Four of five boxes are genuinely closed with live evidence. The fifth (visual List/print/QR verification) is the one concrete carry-over — a manual click-through is recommended before this is called fully done, though nothing found this pass suggests the List UI itself is wrong; it was simply never visually opened this session.

Real defects found and fixed this pass

  • Per-line tax slab was decorative (§05) — confirmed and fixed; see §05 for detail.
  • Corrupted genesis PIH constant (§09) — INITIAL_PREVIOUS_INVOICE_HASH didn't actually decode to SHA256("0"). Fixed in both places it was hardcoded; re-verified independently against the SDK's own -generateHash output and via a real fresh company's genesis invoice reaching a clean global PASS.
  • ICV/PIH hash-chain race condition — the chain-position reservation (getNextHashChainState) had no locking and ran from an un-awaited, fire-and-forget background job (processInvoiceZatca). Two invoices for the same company created back-to-back both read the same "last invoice" and both computed the identical ICV and previous-hash — a genuine fork, reproduced live (two real invoices both landing on icv: 7 with an identical previousInvoiceHash). Fixed by locking the company row (SELECT ... FOR UPDATE, the same pattern already proven for the invoice-number counter) for just long enough to reserve and durably persist the chain position — XML build and signing happen inside that lock (fast, CPU-only), the slow ZATCA network call happens after it releases. Re-verified live: two invoices fired at the exact same instant now get sequential ICVs with an exactly-chained hash, both cleared by the real sandbox. This lock is scoped per company, so it never serializes across different tenants — only two invoices of the same company arriving within milliseconds of each other, which ZATCA's own chain-integrity spec requires to be strictly ordered regardless of implementation.

Addendum — resubmission identity, locked issue time, per-environment chain isolation (BACKLOG.md item 73)

A session focused specifically on anything other than a first-attempt-succeeds submission — a gap this plan's own §03/§04 dual-gate matrix never exercised, since every case there clears on the first try. Checked against all three official ZATCA documents (XML Implementation Standard, Fatoora Portal Manual, Detailed Technical Guidelines — now saved alongside this plan in ZATCA Help/) and the SDK's own sample XMLs, not assumed from the code alone. Found and fixed: resubmission was unconditionally reusing the original ICV/UUID/PIH, directly against the Detailed Technical Guidelines' own stated rule that a rejected document's identity must never be reused; IssueTime drifted on every retry instead of staying locked to the invoice's true creation moment; Sandbox/Simulation/Production shared one continuous ICV sequence with no isolation, confirmed via the Fatoora manual's distinct /simulation/ vs /core/ API hosts to be genuinely separate backends; AccountingCustomerParty was sometimes omitted outright, violating the XSD's minOccurs="1"; nothing guarded against resubmitting an already-cleared invoice or two concurrent submission attempts; and cancelling an invoice that had reserved a chain position but never reached ZATCA permanently wasted that ICV instead of giving it back.

Fixed with a new zatcaChainState table (one row per company+environment, replacing a scan of invoices) and a real reuse-vs-mint-fresh decision keyed on whether the original attempt provably never reached ZATCA and is still the actual chain tip — full detail in BACKLOG.md item 73, including a real self-deadlock bug (an audit-log write from inside a locked transaction referencing the same locked row) caught by the new tests timing out, not by inspection.

Dual-gate re-verified live against CNC Woodcraft & Design (this plan's own seeded demo company, not a throwaway fixture): a real Standard B2B invoice cleared with zero errors (only the already-tolerated BR-KSA-F-08 warning from §09), IssueTime in the actually-submitted XML matched the invoice's creation timestamp to the second, a Credit Note against it cleared with its ICV correctly sequential and PIH correctly chained to the invoice's own hash, and resubmitting the now-cleared invoice was correctly rejected. fatoora -validate on both final XMLs: XSD/EN/KSA all PASSED; the [PIH] FAILED line on both is the same already-documented single-file-isolation limitation noted in §03/item 70, not a defect. Automated suite grew 230 → 238 with dedicated coverage for every scenario above.
