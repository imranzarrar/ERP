QA Results · POS Returns · ZATCA Sandbox

Proving the return/Credit-Note pipeline holds under real ZATCA scrutiny.

BACKLOG item 106 built POS Terminal Returns — full and partial, permission-gated, manager-override-capable — as Credit Notes reusing the same invoice/ZATCA pipeline as every other document in this app, but explicitly deferred real dual-gate verification. This document is that verification: a fresh ZATCA Sandbox onboarding from scratch, then a return-focused test matrix run against ZATCA's real API and the SDK's independent local validator, following this project's own standing protocol (CLAUDE.md, docs/zatca/sandbox-qa-test-plan.html).

Outcome

7 return scenarios run end-to-end against a freshly onboarded throwaway company, each dual-gate-verified. Zero real defects found in return-specific code — cumulative-quantity validation, per-line tax resolution, mixed-tax-rate TaxSubtotal grouping, refund-amount math, restocking, and the manager-override mechanism all held up. One incidental, real Gate-1 rejection was captured for free (a test-fixture mistake, not an app defect) and confirmed the app's rejection-handling behaves consistently for a return the same way it already does for a regular invoice. One pre-existing, non-return-specific gap was observed and flagged for a separate session, not fixed here.

The environment was confirmed reset at the start of this session — a direct database check showed zero companies with zatcaEnabled = true or a completed sandbox onboarding, so nothing here reused state from an earlier pass.

  • Production CSID: ZATCA returned its known static sandbox certificate; the app correctly detected this and switched to ZATCA's matching published sample private key (the already-documented sandbox sample-key adoption from BACKLOG item 40), correcting the stored CR to the shared sandbox value (886431145). isOnboarded became true.

04 / Mixed-tax-rate return, in detail

This project's own historically highest-risk case, re-run for returns

docs/zatca/sandbox-qa-test-plan.html §05 flagged mixed tax rates on one invoice as the highest-risk scenario in this codebase, and a real defect was found and fixed there (item 78) — a single shared header tax rate instead of one TaxSubtotal per distinct rate. This pass checked whether that fix carries through to a return that itself spans two rates, not just an original sale.

Original invoice: 4 units at 15%, 4 units at 0% exempt. Return: 1 of the 15% units and 2 of the 0% units, in a single Credit Note. Result:

  • Refund amount computed correctly: 1 × 120 × 1.15 + 2 × 60 × 1.00 = SAR 258, confirmed against the audit log's recorded refundAmount.
  • The Credit Note's XML carries two distinct cac:TaxSubtotal blocks — one per rate actually present on the return — not one shared block.
  • Real ZATCA sandbox: CLEARED, zero errorMessages; the only warning was the already-tracked BR-KSA-23 (exemption reason code), present because this test's 0% slab has none configured — expected, not a regression.

The per-rate grouping fix generalizes correctly to the return/Credit-Note path without any additional code changes being needed.

05 / Execution results & findings

What actually happened when this matrix was run

Incidental Gate-1 rejection, captured for free

The B2B test customer was initially (accidentally) given the exact same shared sandbox VAT as the company's own onboarded seller identity. ZATCA's real sandbox correctly rejected clearance with a specific, real error:

Real ZATCA sandbox response body
BR-CUSTOM-VALIDATION-01 — The Seller VAT registration number ... must not match the buyer VAT registration number (BT-48).

Fully captured in the audit log (zatca_api_error, HTTP 400, complete validationResults.errorMessages). Both the sale and its Credit Note correctly landed on zatcaStatus: ERROR and never fabricated a false CLEARED. One nuance worth recording: this particular ZATCA response arrived as an HTTP 400, not the "200 with clearanceStatus: REJECTED" shape this app's dedicated REJECTED-status handling is built for — so it was handled via the generic API-error catch path instead. Either path stops clearance correctly and records the real detail durably; this is not a return-specific bug (a regular back-office Invoice against the same customer would fail identically) — the test fixture was fixed (a distinct VAT assigned) and the case re-run cleanly.

Real defects found in return-specific code

None. Every genuine test case, once the test-fixture VAT collision above was corrected, cleared or reported with zero errorMessages from ZATCA's real sandbox API. Cumulative-quantity return validation, per-line tax resolution, mixed-tax-rate grouping, refund-amount math, stock restocking, and the manager-override mechanism all held up under real dual-gate scrutiny. No application code was changed as a result of this pass.

One pre-existing, non-return-specific gap — observed, not fixed here

When ZATCA's real API rejects a submission via an HTTP non-200 response whose body carries no top-level message field (exactly the shape of the incidental rejection above), server/lib/zatca/apiClient.ts's buildZatcaError falls back to a generic message ("ZATCA invoice clearance failed") that ends up stored as the invoice row's own zatcaValidationResults — the real, specific ZATCA error detail (e.g. the exact BR-CUSTOM-VALIDATION-01 wording) survives only in the audit log's zatca_api_error entry, not on the invoice itself. This is identical for any invoice, POS-originated or not, and predates POS Returns entirely. Flagged for a separate, dedicated session rather than touched here, in keeping with this project's own standard of extra caution around server/lib/zatca/ (CLAUDE.md).
