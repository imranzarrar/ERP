The rule

Nothing from 2.0 reaches Live until it has been verified on Demo. Live runs master only: its git pull --ff-only follows master, so v2 cannot reach it by accident. Live's scripts are unchanged and only ever touch the PM2 app erp.

Fixing something on Live while 2.0 is being built

  1. Work in E:\ERP (branch master). Make the fix, test it, commit.
  2. Push, then on the VPS: cd ~/apps/erp && git pull --ff-only && bash deploy/release.sh (as the deploy user).
  3. Bring the fix into 2.0 straight away: in E:\ERP-2.0 run git merge master. Do this every time, so 2.0 never loses a fix.
  4. A Live fix must never depend on a 2.0 table or column: Live's database is the 1.0 schema.

Working on 2.0

  1. Work in E:\ERP-2.0 (branch v2). Its server runs on 3001 against erp_v2; run its tests with TEST_BASE_URL=http://localhost:3001.
  2. Push v2, then on the VPS: cd ~/apps/erp-demo && bash deploy/release-demo.sh (as the deploy user). Schema changes show drizzle's plan first.
  3. To rehearse an upgrade on real data: refresh the demo database from live (below), then release 2.0 onto it and compare.

The demo's data

A scrubbed copy of the live database: deploy/clone-prod-to-demo.sh dumps live over a READ-ONLY connection, replaces the demo database, then runs deploy/scrub-demo-data.sql, which removes every ZATCA key/certificate and switches ZATCA off, clears sessions and reset tokens, gives every user one demo password, and removes emails and phone numbers. Names, documents and amounts are kept so figures can be reconciled. The demo has no SMTP settings and never sets ZATCA_ALLOW_LIVE_CALLS, so it cannot email anyone or call ZATCA Production. Live is only ever read.

One-time VPS setup of the demo (the user runs these, as deploy)

git clone --branch v2 <same repo URL as live> ~/apps/erp-demo
cd ~/apps/erp-demo
bash deploy/setup-demo.sh                 # creates database erp_demo + role erp_demo; touches nothing of live
# create ~/apps/erp-demo/app.secrets BY HAND from deploy/app.secrets.demo.example (new secrets, PORT=4000, HOST=127.0.0.1, APP_ENV=demo)
npm ci && npm run build
bash deploy/clone-prod-to-demo.sh         # copy + scrub live data into erp_demo
bash deploy/release-demo.sh --force-schema   # apply the 2.0 schema (read the plan), start erp-demo on 127.0.0.1:4000

Open the demo from your own machine through an SSH tunnel (nothing is opened in the firewall or Nginx): ssh -L 4000:127.0.0.1:4000 deploy@<VPS> then browse to http://127.0.0.1:4000 (use 127.0.0.1, not localhost, so its cookie never collides with a local app on another port).

Guardrails

  • Both release scripts refuse to run unless folder, branch, database name and port all match their own environment.
  • Secrets never pass through git or chat. The demo's app.secrets is written by hand on the VPS with values that differ from live. The one shared item is the restricted Postgres role erp_app_tenant (the row-level-security policies are written for that name); the demo only gets a GRANT on its own database and the role's password is never changed by the demo scripts.
  • Do not run deploy/setup-rls.sh for the demo: it resets the role's password, which would break Live.

Chapter 3

Platform architecture: how the whole system works

Source: docs/platform/00-platform-architecture.md

This chapter describes what is common to every module, older and new: how a request is scoped to a company, how permissions and row-level security work, how documents are written and reported, how e-invoicing fits in, and how changes are made safely. The list of modules, with their endpoints, tables, screens and tests, is the module catalogue (annex H). The finance core (General Ledger, Receivables, Payables, Bank) is specified in the requirements and design chapters; everything below applies to it as well.

1. Shape of the system

  • One application, two halves. A Node/Express server (server.ts, routes in server/routes/*.ts, shared logic in server/lib/) and a React client (src/) bundled by Vite and served by the same process (port 3000 in development; 3001 for the 2.0 checkout).
  • One database. PostgreSQL through the Drizzle ORM. src/db/schema.ts is the single source of truth for tables; changes are applied with npm run db:push (there are no migration files). Two things db:push does not carry, and which have their own scripts: check constraints and row-level-security predicates.
  • Two tracks. Live (1.0, branch master) takes fixes only; the Demo (2.0, branch v2) takes all new development, including the finance core. See the Environments chapter.

2. Multi-tenancy: every request belongs to one company

  • Every business table carries a companyId. The company of a request, req.targetCompanyId, is resolved once per request in the authentication middleware (isAuthenticated in server.ts) from the signed-in user's own company; only a super-administrator may override it explicitly.
  • A route reads the company only from req.targetCompanyId, never from a query string or body. A reference to another record (a customer id on an invoice) is checked to belong to the caller's company before it is used.
  • Row-level security is the second wall. Every table has a Postgres policy, and request handlers run on a restricted database role (erp_app_tenant) whose connection is told the company (app.company_id) at the start of the request (withTenantDb, tenantDb() in server/lib/tenantDb.ts). A route that forgets a company filter then still cannot see another company's rows. A few platform-administration routes (companies, role templates, onboarding, sessions, ZATCA configuration) deliberately use the unrestricted connection because they act across companies; each says why in a comment.
  • npm run check:isolation is a static check that fails when a route uses a client-supplied foreign key without checking ownership. It is run after every change to a route file.

3. Authentication and sessions

Sign-in creates a server-side session (express-session, stored in Postgres). Automated tests use the documented alternative of an x-session-id header. Passwords are hashed; password reset and company onboarding use emailed links. A super-administrator can list and end sessions.

4. Permissions

  • A user holds roles; the user's permissions are the union of every role, per permission. There is no per-user override on top of roles.
  • Permissions are defined once, in src/permissionSchema.ts, as modules with create / read / update / delete leaves (and a few action leaves such as approving, closing a month or transferring between banks). The same registry builds the role editor and the server checks, through normalizePermissions. Administrators bypass the granular checks.
  • Two separate layers. The permission says whether the person may attempt the action at all; the state of the record says whether it can be touched now (a cancelled record cannot be edited; a cleared e-invoice cannot be edited or cancelled; a converted quotation is final). A route needs both.
  • There is no hard delete of a financial record: documents are cancelled (or reversed), master data is made inactive.

5. How data is read and written

  • Writes go through real routes. Each document type has its own endpoint that applies the business rules (numbering, totals, VAT, period rules) inside one database transaction. There is no bulk "save everything" endpoint, deliberately: it once overwrote posted documents with no period check.
  • The state endpoint is for browsing only. GET /api/state returns the recent rows (capped) so list screens load quickly. Figures are never added up from it.
  • Every report, dashboard figure and list total is computed on the server, for the active company, with no row cap (server/lib/financialReports.ts, server/routes/reports.ts, the ledger report engine). A client never sends a company id for a report. This rule exists because a capped list once silently dropped a tenant's older documents from its own totals.
  • Periods. A document can be created, cancelled or reversed only while its fiscal month is open and its VAT quarter is not filed; the posting guard (assertPostingAllowed) adds the optional lock date and back-date window. The exact rules are in the Accounting rules, Period rule and Posting control chapters.

6. The ledger

Documents (invoices, credit notes, expenses, goods receipts, purchase bills, returns, receipts, vendor payments, manual journals) post to a double-entry ledger through one function, postJournalEntry, which resolves accounts through the company's account mapping and tags lines with customer, vendor and dimensions. What each document posts is in the Posting rules annex; how it works is in the Solution and Technical design chapters. The older document-based reports and the ledger reports are kept consistent by a shared set of facts, and a consistency check compares them.

7. E-invoicing (ZATCA)

  • Every invoice, credit note and debit note goes through processInvoiceZatca(), started after the document's own transaction commits, never awaited by the create request. Credit and debit notes are rows in the invoices table with a document type and a reference to the original; they share the company's hash chain.
  • In order: check the company's e-invoicing switch; record a SUBMITTING status first (so a concurrent cancel cannot see a stale status); reserve the next hash-chain position under a lock held only while building and signing; call the ZATCA clearance or reporting API; store the final status (CLEARED, REPORTED, REJECTED, ERROR).
  • The signed XML is stored compressed and read back only through helper functions. Sandbox, simulation and production are separate identities per company.
  • A cleared or reported invoice cannot be cancelled; a credit note is the only compliant reversal.
  • Changes under server/lib/zatca/ are verified against both the real ZATCA sandbox and ZATCA's own SDK validator (the dual-gate protocol in the ZATCA QA test plan).

8. Screens, language and print

  • Screens are React components (one per module, listed in the catalogue). Every user-visible string goes through a translation function with English, Arabic and Urdu text held in one translation table; the interface mirrors for right-to-left languages.
  • Printed documents (invoices, quotations, vouchers, statements) are drawn by one document renderer from per-company templates, with Arabic and Urdu support.

9. Making a change safely

  1. Check which track the change belongs to; never release Live from the 2.0 checkout or the reverse.
  2. Schema change: edit schema.ts, read what db:push prints before accepting it, then run the check-constraint and row-level-security scripts.
  3. Route change: use the company from the request, check every foreign key, add the permission check, run npm run check:isolation.
  4. Numbers someone will act on come from a server-side computation.
  5. Tests are real HTTP requests against a running server plus direct database checks, with no mocks, and they build their own throw-away company. Run npm run lint and the affected tests; before a release run the whole suite.
  6. New screen text is translated into Arabic and Urdu.
  7. Update the documentation (the skill update-docs-after-development) before saying the work is done.

1. Purpose

Replace document-derived bookkeeping with a real double-entry ledger that sales, purchasing, inventory and (later) payroll all settle into, so that accounts receivable, accounts payable, bank, tax and every financial statement are queries over the same posted lines. This document states, once and traceably, what the business needs; the SRS states what the system shall do about it.

2. Business context and problem

Before 2.0 the system computed every report from documents (invoices, expenses, bills, vouchers). That is correct for a single entity but gives accountants no chart of accounts of their own, no manual adjustments, no analytical dimensions, no subledger tied to a control account, no multi-document receipts, no bank reconciliation and no period control beyond month close. Tier-1 ERP practice (SAP, Oracle, Dynamics) treats all of these as basics.

3. Objectives

  1. One ledger, one posting engine, one report engine: no figure is calculated in two places.
  2. The accountant can see, adjust, analyse and close the books without developer help.
  3. Receivables and payables behave as subledgers: every party balance ties to its control account to the cent.
  4. Money movements (receipts, payments, bank charges) are controlled, auditable and reconcilable to the bank.
  5. Nothing can be posted outside the period rules, and every override is attributable.
  6. The solution serves thousands of concurrent users across many companies, safely isolated.

4. Scope

In scope: 100 business requirements in 14 areas (section 6). 77 are built, 5 partly built, 18 planned.

Out of scope (this programme):

  • Fixed assets and depreciation (classes, CWIP, methods, runs, disposal, transfer, documents) (FR-FA-01..10) — A later phase; the ledger and dimensions are designed not to block it.
  • Landed cost / import costing (FR-LC-01..05) — A later phase tied to procurement.
  • Manufacturing and project work-in-progress costing (FR-WIP-01..08) — No production module yet.
  • Multi-currency, intercompany, payroll calculation ((Blueprint scope)) — Declared out of scope by the Blueprint for this phase.
  • Bank feeds / open-banking integration ((Decision)) — Not requested; statement lines are typed or imported.

BR-JNL-01 Manual journals with maker-checker — Must, Built, Blueprint FR-JE-01, source Decision, sprint S1, S11. BR-JNL-06 Reversal of a manual journal — Must, Built, source Decision, sprint S1. BR-JNL-08 Journal listing and entry detail — Must, Built, source Decision, sprint S1. Every posting of the company, from documents and from manual journals, can be listed and filtered (period, status, source, text) and opened to its lines and its source document.

BR-JNL-09 Opening balances — Must, Built, source Decision, sprint S1. A company that starts using the ledger part-way can post an opening entry: previewed first, balanced (a difference may be put to an equity account), posted once, with a confirmation, and reversible with a reason.

BR-JNL-10 Amount-threshold approval rules — Should, Partial, Blueprint FR-APR-01, FR-APR-02, FR-APR-03, FR-APR-04, FR-APR-05, FR-APR-06, source Blueprint, sprint S11, S11. Approval rules per document type (journal, vendor bill, vendor payment, credit note) by amount, with several sequential levels, server-enforced, with no self-approval at any level and a full approval history; a document without a matching rule posts directly. Version 1.0 / 2026-10-15. Realises the BRD (01) and SRS (02). The detailed mechanics (algorithms, tables, routes) are in the Technical Design (04); this document explains how the solution is shaped and why.

1. Design principles (apply to every future feature)

  1. One place money is recorded. Every module is a source: it decides when and how much, then hands the posting engine a balanced set of lines. AR, AP, bank, trial balance, P&L, balance sheet are queries over the same rows (Blueprint core idea).
  2. A document names who and what, never accounts. The engine resolves control account, bank account, expense-category account and dimension tags from a posting context. No route selects accounts by hand.
  3. Immutable ledger. Posted lines are never edited; a correction is a mirrored reversal plus a new entry, carrying the original tags and parties.
  4. One guard, one engine, one query layer. assertPostingAllowed for every dated posting; postJournalEntry for every write; resolvedLines for every read; reportEngine for every statement.
  5. Tenant isolation twice. Application filter by req.targetCompanyId and PostgreSQL row-level security with composite (company_id, id) keys.
  6. Server-side figures. Nothing a user acts on is computed in the browser or from the capped /api/state.
  7. Architecture first, no patches. A defect is fixed where the rule is enforced (engine, guard, helper), never by adjusting one figure. New behaviour extends the one place that owns the concern.

3. Request lifecycle

4. Posting engine

postJournalEntry(tx, { companyId, branchId, postingDate, docDate?, referenceType, referenceId, description, createdById, lines[], dimensions?, dimensionMode?, context? }).

  1. Sum debits/credits; refuse imbalance beyond the rounding ceiling (a sub-cent difference goes to the ROUNDING role).
  2. loadPostingProfile from the posting context (document party read from the source row by partyOfDocument, or passed explicitly): control account per customer/vendor, bank account per bankId, expense-category account, default dimension combinations.
  3. Each line resolves to an account: explicit accountId → bank account (for role BANK with bankId) → party control account → role mapping (company_accounts.system_key).
  4. Dimension tags merge by priority: line → entry → party → bank → account default; applyRules then drops not-allowed tags and (mode strict, manual journals) refuses missing required ones; resolveCombination find-or-creates one deduplicated combination.
  5. resolvePartyTags sets customer_id / vendor_id on every line whose account has subledger_type customer/vendor.
  6. Insert entry and lines; return the entry id.

reverseAllEntriesFor(tx, companyId, referenceType, referenceId, date, description, userId) finds every unreversed entry of the document, first calls assertNoReconciledLines (a bank line cleared by a reconciliation blocks the whole reversal), then posts each mirror with the original accounts, bank, tags and parties. journal_entries.reversal_of_id is unique, so an entry reverses once.

5. Posting guard (assertPostingAllowed(req, postingDate, { vat, reason }))

Order: (1) open existing fiscal month, not future; (2) VAT quarter (vat: 'none' | 'filed' | 'frozen'); (3) posting_policies.lock_date unless postingControl.overrideLock; (4) max_back_days unless postingControl.backDate; (5) reason when older than reason_after_days; (6) audit BACKDATED_POSTING when an override or a reason was used. No policy row = rules 1–2 only. Every route listed in docs/design-notes/posting-control.md calls it; manual journals call it at submit and approval; settlements and bank adjustments call it from the route.

6. Document dates

doc_date (document), posting_date (ledger; defaults to doc_date via documentDates()), <meaning>_date as Postgres date via the businessDate custom type (string YYYY-MM-DD; raw tx.execute also returns strings). Renames were done in place by scripts/migrate-date-fields.mjs before db:push. Naming rules: docs/design-notes/date-fields-standard.md and skill consistent-column-names.

7. Settlements (server/lib/settlements.ts)

  • openItems(kind, partyId) reuses computeOutstanding (one definition of "owed").
  • recordSettlement: validate amount, bank, party, allocations (checkAllocations: type allowed for the kind, amount > 0, document open for that party, ≤ outstanding, no duplicates, total ≤ amount) → voucher (CustomerReceipt Receipt / VendorPayment Payment, reference_id = party id) → entry (bank Dr / AR Cr, or AP Dr / bank Cr; the engine tags the party) → payment_allocations rows (applied_date) → movePaid updates the document (amount_paid, status; bills use status).
  • applyOnAccount locks the voucher row and allocates up to amount − Σ active allocations.
  • cancelSettlement requires a reason: moves paid amounts back, sets reversed_at/reversed_date, reverseAllEntriesFor, writes a Reversal voucher with reversal_of_voucher_id.
  • assertNoActiveAllocations is called by invoice cancel and cancelExpense.

8. Allocations in the document-based reports (settlementFacts.ts)

allocationEvents turns each allocation into the voucher it would have been had it been paid directly (type Receipt/Payment dated applied_date; a Reversal dated reversed_date). Used for: later-payment adjustment of as-at balance sheets (laterVoucherTotals), cash-basis revenue/expense recognition, outstanding figures. onAccountBalances(asOf) = settlement vouchers up to the date not cancelled by then, minus allocations applied and not reversed by then → Customer advances (liability) / Vendor advances (asset) in computeBalanceSheet and computeTrialBalance; Ledger-vs-Documents compares AR/AP net of them. Statements and cash flow read the settlement voucher itself (full amount, own date). Reversal direction is one rule: reversalIsCashOut(referenceType).

9. Subledger (server/lib/subledger.ts)

Balance per party = Σ(debit − credit) of lines tagged with the party on the control accounts. Aging = balance-forward: charges aged from their document date, credits (payments, credit notes, receipts on account) set against the oldest charge first; an unapplied credit shows in an On account column; buckets Not due / 1–30 / 31–60 / 61–90 / Over 90 (labels from the report). reconciliation returns control-account balance, aging total, difference and untagged lines. Consistency rules R8.1–R8.4 prove: no untagged control line, parties sum to control accounts, aging equals balance.

10. Bank reconciliation (server/lib/bankReconciliation.ts)

  • Bank ledger account = company_accounts.bank_id; its lines are resolvedLines with that account id.
  • Lines shown for a session: outstanding at its date (bank_reconciliation_id IS NULL or cleared by a later session) plus those it cleared.
  • Summary: book = Σ lines ≤ date; cleared = Σ lines cleared by this session or an earlier Completed one; difference = statement − cleared; deposits in transit / payments outstanding = uncleared debits / credits. Identity: statement + deposits in transit − payments outstanding = book when difference = 0.
  • Completion: difference = 0 and no unmatched statement line; stores gl_balance_at_reconciliation.
  • Adjustment: voucher (BankCharge Payment or BankInterest Receipt) + entry (bank against an active, postable Expense (charge) or Revenue (interest) account), line cleared and matched. Reversal: reverseAdjustment un-matches, un-clears, reverses entry, writes Reversal voucher.
  • Legacy statements read the charge/interest figures from the ledger entry: bankAdjustmentRows/Totals in financialReports.ts feed P&L, trial balance, balance sheet (open months), month P&L, dashboard and cash flow.
  • Reopen: latest completed session of the bank only; no other session in progress; audit BANK_RECONCILIATION_REOPEN.

11. Report engine (server/lib/reportEngine.ts)

Definition = rows × columns. Rows: Heading, Accounts (selectors: account, parent rollup, range, type, role; include/exclude; value rule Net/Debit/Credit/Debit-only/Credit-only/Split; show rule), Subtotal, Calculated (formula over row numbers), Text, Spacer, ProfitToDate. Columns: periodBasis × valueBasis × presentation × optional dimension filter, plus variance columns. Per column the engine fetches per-account debit/credit totals once through resolvedLines. Every cell returns { accountIds, from, to, dims, basis } for drill-down. Formatting is validated by one shared module. The legacy /reports/trial-balance is an adapter over the seeded definition.

11a. Approvals (server/lib/approvals.ts, server/routes/approvals.ts)

  • Tables: approval_rules (document type, amount band: above min_amount up to and including max_amount, priority), approval_rule_levels (1..5; approver type Role / User / Permission / Manager with manager_steps), approval_requests (intent payload, rule snapshot levels, current level, status, submitter, self_approved, result_document_id), approval_actions (append-only). users.manager_id feeds the Manager approver; the users route (server/routes/users.ts) validates it (same company, not self, no loop up to 20 hops) and the user form in Settings sets it.
  • submitForApproval(tx, req, {documentType, amount, summary, payload}): lowest-priority active rule whose band contains the amount; none = {pending:false} and the caller continues exactly as before.
  • decideRequest: row-locks the request; refuses the submitter unless companies.journal_self_approval is on; checks the level authority (holdsLevelAuthority), that the actor has not acted before, requires remarks to reject; on the last approval calls the registered executor, which runs assertPostingAllowed for the approver and creates the document as the submitter. Any refusal rolls back the whole decision (no action row is kept).
  • Recall: recallRequest (submitter only, pending only; action row Recalled, status Recalled). Chapter 9

Accounting and reporting rules

Source: docs/design-notes/accounting-rules.md

These are the rules the system must obey. Every report is derived from the documents by these rules; GET /api/reports/consistency-check (server/lib/consistencyCheck.ts) tests them for any company at any time. When a figure ever disagrees with another, find which rule is violated and fix the rule's enforcement — never adjust the one figure.

A. Dates

  • A document that carries a user-chosen date (invoice, expense, purchase bill) must be dated in an existing, open fiscal month, not in the future, and outside any VAT quarter whose return is generated or filed.
  • Everything else is dated the day it is entered: goods receipt, stock movement, credit note, vendor return, payment, refund, reversal, stock adjustment, cancellation. A payment cannot be dated before the document it pays.
  • The stock register files each movement under the day it physically happened.

B. Locking

  • A closed month locks every document dated in it. A generated or filed VAT quarter locks every tax document dated in it (invoice, credit note, expense, bill, vendor return, and their cancellations).
  • A locked document is never changed, cancelled or dropped from its period. Reports for a locked period never move (closed months keep their stored profit; filed returns keep their figures).
  • A VAT return that is only generated freezes its quarter until it is deleted; a filed return is permanent.

C. Corrections

  • A document that is not locked may be cancelled (invoice not reported to ZATCA; expense; bill; return; GRN before billing). A cancelled expense posts its reversal on the day of cancellation.
  • A locked document is corrected only by a new document dated today, landing in the current open period and quarter:
    • sales invoice → credit note (its own date = issue date; the original invoice date stays on the original);
    • goods receipt / purchase bill → return to the vendor (reduces stock; reduces what is owed, or becomes a vendor credit receivable if the bill was already paid; VAT adjusted in the quarter of the return);
    • expense → reversal document (negative expense, same treatment as above);
    • money back from a vendor → vendor refund (clears the vendor credit).
  • A corrected-by-document original is never edited or removed; the correction is a separate dated event.

D. What each figure means

  • Revenue / COGS / expenses are by document date, tax-exclusive. Credit notes and reversals count negative in the period they are issued.
  • Stock is a Balance Sheet item: quantity on hand × average cost from goods receipts. A stock item sold before it is received simply carries cost 0 until stock arrives; a typed (non-stock) line never has a cost.
  • Accruals are estimates: owed at their net amount, no input VAT. The real invoice that settles one claims its own VAT, in its own period, and adds only the difference to cost.
  • VAT follows tax-invoice dates: output VAT = sales register, input VAT = purchase register (bills and expenses at original amounts, minus returns/reversals in their own periods).
  • As-at reports (Balance Sheet / Trial Balance for an earlier date) show what was owed and held on that date.

E. The checks (see consistencyCheck.ts)

R1 the books balance · R2 every balance ties to its register (bank, receivables, payables, inventory, VAT, profit) · R3 stock register = quantity on hand · R4 locked periods never move · R5 the books balance at every earlier month end · R6 the journal agrees with the documents.

Period rule for cancel, reversal, return and credit

Source: docs/design-notes/reporting-rules.md

  1. A document can be cancelled, reversed or returned only while its own fiscal month is open and its VAT quarter is not filed. Otherwise the action is refused. While the period is open, treating the cancelled document as void in that period is correct, because nothing closed changes.
  2. A closed month or a filed VAT quarter is never touched and never corrected afterwards.
  3. A later correction is a NEW document dated today (credit note, purchase return, refund, supplier credit). It lands in the current open period and the current VAT quarter.
  4. Cancelling an expense posts its reversal on the day of cancellation.
  5. Every dated entry (bill, payment, refund, stock adjustment, cancel) must fall in an existing, open month and outside a filed quarter.

Guard: tests/closedPeriodImmutability.test.ts attempts every cancel, reversal, credit, return, payment, settlement and delete against a closed, filed period; each must be refused or leave the period unchanged, and the books must stay balanced.

Considered and not adopted: a cancelledAt column, retroactive VAT correction of a closed quarter.

Naming

  • A system moment (set by the program, never typed) is <meaning>_at, type timestamp. Who did it is <meaning>_by_id.

Posting control: the lock date and back-dating rules (Demo / 2.0)

Source: docs/design-notes/posting-control.md

Built 2026-10-15 after the question "what is the rule for back-dating, and what do tier-1 ERPs do". Tier-1 systems (SAP posting periods, Oracle GL calendar, Dynamics ledger calendar) do not count "days back"; they control back-dating with period status, authorisation and audit. This is that, on top of what the system already had (open / closed fiscal month, VAT quarter freeze, ZATCA no-edit rule).

The rules, in the order they are checked (server/lib/postingGuard.ts, one function for every route)

  1. Fiscal month: the posting date must be in an existing, open month, not a future month. (Unchanged.)
  2. VAT quarter: a tax document may not be dated in a generated or filed quarter; any other posting may not be dated in a filed quarter. (Unchanged.)
  3. Lock date (posting_policies.lock_date): nothing may be dated on or before it, except by someone holding postingControl.overrideLock.
  4. Back-date window (max_back_days): nothing may be dated more than N days before today, except by someone holding postingControl.backDate. 0 = dated today or later.
  5. Reason (reason_after_days): a posting older than N days must carry a reason (backDateReason in the request; a manual journal keeps it on the journal so the approver does not retype it).
  6. A posting that used an override, or that carries a reason, is written to the audit log as BACKDATED_POSTING (route, posting date, days back, reason, which override).

With no policy row (a company that never opens the screen) only rules 1 and 2 apply, exactly as before. The administrator holds every right.

What is covered

Every route that posts something dated, or reverses something at its own date, calls the guard: invoices (create, credit note, cancel, quotation conversion, payment), POS returns, expenses (create, pay, reverse, cancel, recurring and accrual settlement), purchase bills (create, pay, cancel), purchase returns and cancellations, GRN reversal, vendor refunds (and their cancellation), stock adjustments and stock-take finalisation, inter-bank transfers, investor contributions, opening balances (post and reverse), and manual journals (at submit and again at approval). A quotation posts nothing, so it keeps the open-month rule only.

The date the rules judge is the posting date. A manual journal may have a posting date apart from its document date: a journal dated in a locked period but posted today is allowed; the reverse is refused.

Permissions (Roles screen, General Ledger group "Posting Control")

read (see the screen), update (change the policy), backDate (post beyond the window), overrideLock (post on or before the lock date). Everyone signed in can read the policy, so forms can ask for a reason.

Not built yet (from the tier-1 comparison, the next step of period control)

  • a restricted month status between Open and Closed that only named users can post into, and the adjustment period after year-end (fiscal_months.is_adjustment_period, Blueprint FR-YEC);
  • per-module close (AR, AP, inventory, GL closing on their own dates);
  • an approval route for a back-dated posting above an amount (Blueprint FR-APR).

Tests

tests/postingControl.test.ts (8): policy permissions and validation, no policy = no change, the window and its override with audit, the same rule on expenses and journals, the lock date including the cancellation of an old invoice, the reason rule from draft to approval, and a posting date apart from the document date.

AR, AP and bank reconciliation: design against the Finance Core Blueprint (Demo / 2.0)

Source: docs/design-notes/ar-ap-bank-design.md · Decision record: written before building, with an as-built section

Written 2026-10-15 before building (architecture-first). Sources: docs/reference/Finance-Core-Blueprint.pdf (FR-AR-01..03, FR-AP-01..04, FR-BANK-01..05, data model pages 21-28), docs/design-notes/gl-step1-5-decisions.md (posting profiles, control accounts), the code as it stands.

What the code already has

  • Invoices, credit notes, expenses and purchase bills post to the ledger through postJournalEntry, and since slice 1b the receivable / payable line lands on the party's control account.
  • A payment is a voucher (Receipt / Payment / Reversal) plus a journal entry, created inline by about ten routes. A voucher points at ONE document (reference_type, reference_id). invoices.amount_paid / payment_status are kept by those routes.
  • Customer / vendor statements, "Outstanding Aging & Balances", the customer / vendor balance on a screen: all computed from the DOCUMENTS (invoices, vouchers ...), not from the ledger.
  • No bank reconciliation. No customer-tagged ledger line. No receipt applied across several invoices, no payment on account.

What the Blueprint requires (and the gap)

Requirement Gap
FR-AR-01 a posted invoice / credit note posts to the AR control account tagged with the customer the line is on the right account, but carries no customer: journal_lines.customer_id / vendor_id do not exist
FR-AR-03 aging and statements are a live query over posted journal lines on the control account, never a separate balance they are document-based
FR-AR-02 / FR-AP-04 a receipt / payment applies across one or more open invoices / bills, or is held on account, through a payment allocation record one voucher = one document; nothing on account
FR-AP-02 expenses and bills share one AP control account and vendor subledger true for the account; the vendor tag is missing, so one vendor position cannot be read from the ledger
FR-BANK-01..05 reconciliation session per bank per statement period, uncleared lines, live formula, complete only when it balances, discrepancy by journal entry, completed lines locked, reopening needs permission and is audited nothing
FR-JE-04 / FR-APR-01..05 approval rules per document type and amount not built (journals have maker-checker only)

Decisions

  1. The subledger is the ledger. journal_lines gain customer_id and vendor_id (typed, nullable, composite FK to the party within the company), set by the posting engine from the same party context that already picks the control account (server/lib/postingContext.ts): no route sets them. Existing lines are back-filled from their source document by an idempotent script. Whatever posts to a customer's receivable line carries that customer.
  2. Aging, ledger and statements are queries over those lines (server/lib/subledger.ts): a party's open balance is the sum of its lines on the control account(s); aging buckets by document due date with payments and credit notes matched oldest-first (the balance-forward method) until the allocation record (decision 4) exists, then by explicit allocation. Both agree to the cent by construction; a consistency rule proves control account = sum of party balances + unallocated.
  3. A consistency rule per control account joins the existing checks: the control account's ledger balance equals the sum of every party's balance, and no ledger line on a customer control account lacks a customer.
  4. Payment allocation (FR-AR-01, FR-AP-03): table payment_allocations (company, voucher, allocated-to type + id, amount, created at/by). A receipt or payment is still a voucher + journal entry; the allocation says which documents it settles. Every existing path that creates a Receipt / Payment voucher goes through one function (recordPaymentAllocations) so documents' amount_paid and the allocations cannot drift; a back-fill creates the allocations of history. New screens: Receive Payment (a customer, a bank, an amount, the open invoices to settle, the rest held on account) and Pay Vendor (the same for bills and expenses), plus apply credit note / on-account credit to an open invoice.
  5. Bank reconciliation exactly as FR-BANK-01..05: bank_reconciliations (bank, statement date, ending balance, GL balance at reconciliation, status, completed by / at) and bank_statement_lines (date, description, amount, matched ledger line); journal_lines gain bank_reconciliation_id and reconciled_at. A session lists the bank account's posted, uncleared lines; statement lines are typed in or imported (CSV / Excel) and matched by amount and date (suggested, never silent); completion is blocked unless Book balance + outstanding deposits - outstanding payments = statement balance; a bank charge or interest is posted as a journal entry from inside the session; a completed session locks its cleared lines; reopening needs a permission and is audited.
  6. Voucher and posting print-outs: the Receipt / Payment voucher print gains the posting (accounts debited and credited, with the party and the allocations); a new Journal Voucher print for a manual journal and for any posted ledger entry. Same print pipeline as every other document (templates, Arabic / RTL), no second renderer.
  7. Approval rules (FR-JE-04) stay for a later step; the guard in postingGuard.ts is where an approval check would hook in.

Build order (each step complete: schema, RLS and keys, engine, routes, permissions, screens, translations, tests, docs; deployed to the Demo)

As built (2026-10-15): where the build differs from, or settles, the design above

  • Allocation dates. payment_allocations also carries applied_date and reversed_date (business dates, not timestamps): "as at" reports must read the day the money was put against a document, not the day the row was typed. server/lib/settlementFacts.ts turns allocations back into the per-document vouchers the older reports expect, and is the single place that knows both shapes.
  • Money held on account is a liability (Customer advances) or an asset (Vendor advances) in the document-based Balance Sheet and Trial Balance, and is netted into AR / AP when the ledger is compared with the documents (the ledger has one receivable and one payable account; the documents show the advance as its own line).
  • Reversal vouchers and cash direction. One rule, reversalIsCashOut(referenceType) in financialReports.ts: a Reversal undoing a receipt (Invoice, VendorRefund, CustomerReceipt, BankInterest) is money out; undoing a payment is money in.
  • The reconciling formula is built the standard way: statement balance + deposits in transit − payments outstanding = book balance, i.e. cleared balance = statement balance. (The Blueprint prints the two outstanding terms with the opposite signs; the arithmetic of a real bank reconciliation is the one used.)
  • Bank fee / interest is not a free-form journal: money cannot leave a bank without a voucher in this application (every bank balance, the bank ledger and the Balance Sheet read vouchers), so the adjustment writes a voucher (BankCharge payment / BankInterest receipt) and the ledger entry, restricted to an expense account (charge) or an income account (interest). The bank-charge / interest figures are read from the ledger entry (as Cost of Goods Sold is) into the Profit & Loss, the month-close figure, the Trial Balance, the dashboard profit and the cash flow, so every document-based statement still balances.
  • Locking. "A completed reconciliation locks its cleared lines" is enforced where reversal happens: reverseAllEntriesFor (ledger.ts) refuses to reverse an entry that has a bank line cleared by a reconciliation. The cancel of a receipt / payment / invoice payment therefore fails as a whole (its transaction rolls back), with a message naming the way out (un-clear, or reopen).
  • Print model. Vouchers, journal vouchers and the reconciliation statement are printed from one server-resolved payload (server/lib/postingPrint.ts: entries with account, party and dimension labels), rendered by DocumentRenderer as three new internal document types that follow the viewer's language and direction.
  • Permissions follow the Blueprint list (bankReconciliation: create, read, match, complete, reopen) plus one added leaf, adjust, because posting an entry is a different authority from ticking lines.

Known deviations from the Blueprint (deliberate)

  • Approval is the simple maker-checker already built; amount-bracket approval rules stay a later step.

Control accounts and posting profiles (decided after the user asked: "select a party or item in any transaction and the rules apply automatically")

What the documents say: control accounts are accounts only a subledger may post to (FR-COA-02, glossary); a line carries the customer / vendor / tax tag as a strongly typed field (FR-JE-03, ERD); bank_accounts gain a linked GL account, tax_slabs gain Output/Input VAT account links, product categories replace the free-text glGroupMappings with real account keys (ERD "Modified" list); default dimensions flow from the context to the line (Dynamics model the user chose). What the code does: a document names a posting ROLE (AR, AP, INVENTORY, SALES_REVENUE, COGS ...) and postJournalEntry stamps the company's current account for that role; banks and expense categories already resolve to their own account; customers, vendors, products and tax slabs have no account or dimension defaults.

Decision: one resolution step, inside the posting engine, driven by a posting context. A document does not pick accounts; it passes WHO and WHAT it concerns, and the engine resolves accounts and dimension tags.

  1. company_accounts gains subledger_type (customer, vendor, inventory, bank, tax, asset, none). A control account is an account with a subledger type; only that subledger's documents post to it (manual journals keep refusing them). Several control accounts per type are allowed (Trade receivables, Staff receivables); the role account (AR, AP ...) remains the company default.
  2. Master records may point at their control account (customers.control_account_id, vendors.control_account_id; only a control account of the matching subledger type is accepted), and at default dimensions (default_dimension_combination_id, a combination exactly as on a ledger line) on customers, vendors, products/categories, banks. Tax slabs get their Output/Input VAT accounts; product categories get inventory / sales / COGS accounts (replacing the free-text GL groups).
  3. postJournalEntry takes an entry-level context ({ customerId, vendorId, branchId, bankId, productCategoryId, taxSlabId }). Role lines resolve first through the context (customer's control account, bank's own account, category account, slab account), then through Account Mapping (today's behaviour); dimension tags merge in this priority: line-specific, product/category, customer/vendor, bank, branch, account default; then the account rules decide what is allowed or required.
  4. Because every document already calls postJournalEntry, existing routes only gain a context argument; no route re-implements account selection.
  5. The strongly typed customer_id / vendor_id tags on journal_lines arrive with AR/AP (so aging becomes a query over control-account lines), and a consistency rule checks every control account against the sum of its subledger.
  6. Order: dimension framework core (in progress) -> posting context and master defaults (slice 1b) -> report engine -> AR -> AP. Product-category revenue/COGS splitting needs line-level product context and is part of slice 1b only for accounts the documents already know (customer, vendor, bank, branch, tax slab); per-category revenue lines follow with AR.

Source: docs/design-notes/approval-rules-tier1-research.md · Decision record: Sprint 11 research and owner decisions

Written 2026-10-15 for BR-JNL-10 (Blueprint FR-APR-01..06). Based on the documented behaviour of SAP S/4HANA, Oracle Fusion / NetSuite, Microsoft Dynamics 365 Finance and Odoo as I know them; not re-verified against current vendor documentation, so confirm details before quoting them externally.

2. Principles every tier-1 system shares (these are the requirements, regardless of vendor)

  1. Rule-driven, not blanket. Only documents matching a rule enter approval; everything else posts directly (our FR-APR-06). Approval is overhead on high-value or sensitive items.
  2. Nothing hits the ledger (or releases funds) until approved. The document sits in a pre-posted state (parked / pending); reports and subledgers never see it.
  3. Separation of duties enforced by the server. The submitter can never approve their own item at any level; a second control is that approvers cannot approve beyond their own authority limit.
  4. Authority by amount band and by role, not by named person alone; approvers are resolved from roles / hierarchy so staff changes do not break rules.
  5. Sequential levels above higher thresholds, with parallel/any-of options at one level.
  6. Immutable history: who, when, level, decision, remarks; visible on the document.
  7. Changing a pending document invalidates approvals (edit = recall and resubmit, or re-approve if the amount rises).
  8. Delegation and escalation for absence and delay (substitute with validity dates; escalate after a timeout).
  9. Rejection returns to the submitter with remarks; nothing rejected ever posts.
  10. Payments are the strictest case: dual control, and blocked payments are excluded from payment runs.

3. What we already have (do not rebuild)

  • Manual journals: Draft → Pending → Posted with maker-checker, rejection with reason, optional self-approval switch, event history (manual_journals, manual_journal_events). This is a single-level, always-on rule hard-wired into the journal route.
  • Posting guard, audit log, permission registry, per-document posting paths.
  • Documents that post immediately today: vendor bills, expenses, receipts, vendor payments, credit notes.

4. Recommended design for Sprint 11 (fits our architecture)

One generic approval engine, not one workflow per document. The manual-journal maker-checker becomes the first client of the engine; bills, payments and credit notes follow.

4.1 Data (all company-scoped, RLS, composite keys)

  • approval_rules — company, document type (Journal, VendorBill, VendorPayment, CreditNote, later Receipt, Expense), name, active, amount from / to, optional conditions (branch, vendor, currency-free), priority, effective dates.
  • approval_rule_levels — rule, level number, approver type (Role | User | Permission), approver id, mode (Any one | All), optional amount ceiling per level, escalation days.
  • approval_requests — one per submitted document: document type + id, rule used (snapshot of the levels at submit time), status (Pending, Approved, Rejected, Recalled), current level, amount at submit, submitter, timestamps.
  • approval_actions — request, level, actor, action (Approved, Rejected, Delegated, Escalated, Recalled), remarks, time. Append-only.
  • approval_delegations — delegator, delegate, document types, valid from/to.

4.2 Engine behaviour

  1. A document route calls submitForApproval(type, id, amount) instead of posting. The engine finds the matching active rule (lowest priority number wins; band by amount); no match → returns "post directly" (FR-APR-06).
  2. A match creates the request, sets the document status to Pending Approval and posts nothing. Vendor payment: no voucher, no bank movement, excluded from any payment run.
  3. decide(requestId, level, action, remarks) is the only way forward: checks the caller holds the level's authority (role/permission/delegation), is not the submitter (FR-APR-03, server-side), and has not already acted at an earlier level.
  4. Last level approved → the engine calls the document's own post function inside the same transaction; the posting guard runs again at that moment (as manual journals do today).
  5. Reject → document returns to Draft with remarks; edit of a pending document recalls the request; an amount increase restarts approval.
  6. Everything is audited and shown in the document's history; a worklist screen ("My approvals", with counts in the menu) lists what waits for the signed-in user.

4.3 Screens

Approval Rules (list, rule editor with levels and amount bands, test-a-document preview), My Approvals (worklist, bulk approve for same-rule items), history panel on every document, delegation settings.

4.4 Permissions

approvalRules (create, read, update, delete); approvals.decide is not a global right: authority comes from the rule's level (role/permission), so a person can approve vendor payments up to a band without being able to approve journals. Optional approvals.override for an owner emergency approval, audited.

4.5 Rollout safety

  • Default = no rules = today's behaviour exactly (journals keep their single-level flow until an owner defines a rule, then the engine takes over).
  • Migrate journals last, after bills and payments prove the engine.
  • Tests: threshold boundary (equal to / just above), two-level chain, submitter never approves, same person cannot approve two levels, delegation window, amount change restart, rejection path, posting guard re-check at approval, payment excluded until approved, cross-company isolation.

5. Decisions needed from the owner before building

  1. Which documents first? Recommended: vendor payments and vendor bills (money out), then credit notes, then fold manual journals into the engine.
  2. Approver model: roles only (simplest), or roles plus the user's manager hierarchy? Our users have roles but no manager hierarchy today; recommended roles + named users in v1.
  3. Self-approval: keep today's company-level switch for journals, or forbid absolutely for payments (recommended: absolute for payments).
  4. Currency of thresholds: company currency only (single-currency scope).
  5. Delegation and escalation in v1? Recommended: delegation yes (absence is real), escalation to v1.1.
  6. Approval by email/mobile? Recommended: not in v1 (in-app worklist and notification count only).
  7. Should reopening a bank reconciliation, overriding the lock date or back-dating also route through approval? Tier-1 systems usually keep these as authority rights, not workflow; recommended: keep as rights.

6. Out of scope for S11

Parallel multi-branch routing by cost-centre hierarchy, e-signature, scheduled auto-approve, approval by external email links.

7. Owner decisions (2026-10-15) — binding for Sprint 11

  1. Order: vendor payments and vendor bills first, then credit notes, then manual journals folded into the engine.
  2. Approvers: roles and the manager hierarchy. Users gain a manager link (users.manager_id, additive, nullable) and a rule level may name "manager of the submitter" (and the manager's manager, up to N steps) besides a role, a user or a permission.
  3. Self-approval: a company-level setting in General Ledger settings, on or off. Off (the default) = a submitter can never approve their own document at any level; on = allowed, the document is flagged "self-approved" and the setting change and every use are audited. The setting covers payments, bills and credit notes as well as journals (today's journal switch becomes this one setting).
  4. Delegation with validity dates in version 1; escalation after a timeout in 1.1.
  5. Notification inside the system only: a "My approvals" worklist and a count in the menu. No email or mobile.
  6. Back-dating, lock-date override and reopening a reconciliation remain authority rights, not workflow.

Annex E — Developer guide for future ledger work

Source: docs/gl-ap-ar/annex-e-developer-guide.md

Read the Solution Design (03) principles first. This page is the practical checklist.

Add a new source document that posts

  1. Do not pick accounts. Call postJournalEntry with referenceType, referenceId, role lines, and a context (or let partyOfDocument read the party). Add the document type to partyOfDocument (postingContext.ts) and to the party back-fill (scripts/backfill-party-tags.ts) if it touches a customer/vendor.
  2. Call assertPostingAllowed(req, postingDate, { vat }) before writing; give the document doc_date + posting_date (documentDates()).
  3. Reversal = reverseAllEntriesFor (it already honours the bank-reconciliation lock).
  4. If the document moves cash, write a voucher (every cash movement is one) and decide its reversalIsCashOut direction.
  5. If older reports must see it, extend the single translator (settlementFacts.ts / financialReports.ts), not each report.
  6. Add rows to Annex D, tests, translations, permission leaf (registry first, then the route check), audit call.

Route a document through approval rules

In its create route, build the document's intent (payload), call submitForApproval; if pending, return {pendingApproval: true, requestId} and write nothing. Register an executor with registerApprovalExecutor(type, { execute }) that runs the posting guard for the approver and creates the document as the submitter. Add the type to SUPPORTED in server/routes/approvals.ts. Refuse any shortcut that would create the document without the rule (see the goods-receipt flow).

Add a table

Company column + RLS policy + index + composite (company_id, id) unique if referenced; db:push; apply-rls-policies.mjs; add to pre-push-keys.mjs if an existing populated table gains the unique key; build routes on withTenantDb; isolation test; check:isolation.

Add a report

Prefer a report definition (rows × columns) over code. A new figure must come from resolvedLines; compute server-side for req.targetCompanyId; no row cap.

Add a screen

src/components/ledger/*, route case in LedgerModule.tsx, menu item in App.tsx (permission key), title and subtitle, translations in src/glTranslations.ts, print through PrintDocContext (usePrintDoc).

Add a permission

src/permissionSchema.ts (grantable) and hasPermission in the route (enforced). Separate authority gets its own leaf (see bankReconciliation.adjust).

Date and naming rules

doc_date, posting_date, <meaning>_date (type date), created_at/by, updated_at/by; snake_case in the database, camelCase in code and API.

Verification before you say done

npm run lint · npm run check:isolation · new tests · TEST_BASE_URL=http://localhost:3001 npx vitest run · consistency check clean · translations applied · npx tsx scripts/build-gl-docs.mjs --check · docs rebuilt.

Do not

  • Adjust one figure to match another; find the rule and fix its enforcement.
  • Add a bulk "save everything" route.
  • Select accounts in a route, or compute a report in the browser.
  • Run a Live release script from the 2.0 checkout, or merge v2 into master.

Part 3 — Everything learned from the RLS / inventory release (2026-09-19). Read before moving hosts.

3a. Row-Level Security needs its own one-time setup (a fresh server, or the first deploy that contains RLS)

Order matters; each step needs the previous one:

  1. bash deploy/setup-rls.sh — creates role erp_app_tenant (LOGIN, NOSUPERUSER, NOBYPASSRLS) and grants it DML on all tables (+ default privileges for future tables). It prompts for a password.
  2. Put TENANT_DB_USER=erp_app_tenant and TENANT_DB_PASSWORD=<same password> in app.secrets by hand. Use a password of letters and digits only (e.g. openssl rand -hex 20): dotenv treats #, $ and quotes specially, and a mismatched password makes every tenant-scoped request fail with "password authentication failed for user erp_app_tenant". (That is exactly what happened on the first deploy: pages loaded forever, see the log line in pm2 logs --err.)
  3. Deploy with bash deploy/release.sh --force-schema (its db:push step: read the plan, only policies/indexes expected).
  4. npx tsx scripts/apply-rls-policies.mjs — mandatory after every db:push: drizzle-kit creates policies but drops their USING/WITH CHECK conditions.
  5. bash deploy/verify-rls.sh (must print RLS OK) and npx tsx scripts/verify-tenant-isolation.ts (must print ALL ISOLATION CHECKS PASSED; it creates two temporary companies inside a transaction that is rolled back — nothing is left behind). Also: Postgres max_connections must cover, per PM2 instance, the normal pool plus the tenant pool (TENANT_DB_POOL_MAX, default 10).

3b. Nginx performance setup (not optional)

bash deploy/nginx-tuning.sh <domain> after Certbot. It (1) adds HTTP/2 to the 443 listeners, (2) turns on gzip for JS/CSS/JSON — Ubuntu's stock nginx.conf only compresses HTML because gzip_types is commented out, and (3) caches the content-hashed /assets/ files for a year (immutable) while leaving index.html uncached so deploys show up immediately. Verify: curl -sI -H 'Accept-Encoding: gzip' https://<domain>/assets/<index-hash>.js → HTTP/2 200, content-encoding: gzip, cache-control: public, max-age=31536000, immutable. Why each matters (measured): over HTTP/1.1 a burst of ~110 requests queued for ~6 s behind the browser's 6-connection limit; the bundle was 2.1 MB raw with max-age=0.

3c. Client delivery, so the app stays fast as data grows

  • The JS bundle is split: first load ≈ 0.5 MB (152 KB gzip); each screen is fetched on first use (React.lazy in src/App.tsx); react/charts/motion are separate stable chunks (vite.config.ts).
  • The UI dictionary is not in /api/state any more: GET /api/translation-bundle?lang= (user's language only; all three for super-admins) with a content-digest ETag → repeat loads are a 304.
  • Browsers no longer auto-register missing translation keys in production (ALLOW_TRANSLATION_AUTOREGISTER=true re-enables it, off by default); new keys ship through reviewed changes. In dev it still works, batched (POST /api/register-missing-keys).

3d. Diagnosing "the site is slow" — check the network first

Two separate times a slowdown blamed on the release was the user's own connection (packet loss, 2-4 s TLS handshakes) while the VPS sat idle. Before touching code: (1) top + pg_stat_activity on the VPS (idle = not the server); (2) from the affected machine, curl -w "connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}" against the site and against a well-connected site for comparison, plus ping for loss; (3) browser Network tab → the slow request's Timing → "Waiting for server response". Locally, saving an invoice takes ~20-65 ms with RLS on, so multi-second saves point at the path or at an external call, not the database.

3e. Gotchas

  • Never source app.secrets in bash: a value with an unquoted space makes bash try to run its second word as a command (Compbrain: command not found). Read single keys with grep/cut instead.
  • deploy.sh exits early ("Already up to date") if the code was already pulled by hand — then the build/reload never ran. If unsure, run npm run build && pm2 reload deploy/ecosystem.config.cjs.
  • New shell scripts checked in from Windows lose their executable bit; run them with bash deploy/<script>.sh (or git update-index --chmod=+x).
  • After a deploy, users with a stale cached page may see a blank screen once; a hard refresh (Ctrl+Shift+R) or "Clear site data" fixes it.

3f. Ad-hoc production Postgres access from a local machine

Postgres on the VPS stays bound to 127.0.0.1 (confirmed via sudo ss -tlnp | grep 5432) and is never exposed publicly — port 5432 is not, and must never be, opened in ufw. For a one-off local query or inspection, tunnel instead of exposing anything: bash deploy/db-tunnel.sh (run locally, not on the VPS) forwards localhost:5433 to the VPS's localhost:5432 over the existing SSH access, then connect with psql -h localhost -p 5433 -U <SQL_USER> -d <SQL_DB_NAME> (credentials from app.secrets on the VPS). The SSH process is the tunnel — closing that terminal kills it; use --background to keep it alive after closing the window.

3g. Showing a "system unavailable for maintenance" page

For real downtime (a VPS reboot test, a risky migration, anything where the app or Postgres might actually be stopped), an in-app banner can't help — if the app can't boot, there's nothing left to render one. Instead, deploy/maintenance.html is a static page served directly by Nginx, independent of the Node app.

One-time setup (per site, do this once): add a single line to the live HTTPS server block in /etc/nginx/sites-enabled/<name> (NOT the plain :80 redirect block), right after its server_name line:

include snippets/erp-maintenance.conf;

Then install the snippet and validate before reloading:

sudo mkdir -p /etc/nginx/snippets
sudo install -m 644 deploy/nginx-snippets/erp-maintenance.conf /etc/nginx/snippets/erp-maintenance.conf
sudo nginx -t && sudo systemctl reload nginx

High Availability Plan (for review)

Source: docs/proposals/high-availability-plan.md · Proposal: nothing built yet

Status: proposal, nothing built yet. Written 2026-09-22 in response to Hostinger's notice that VPS maintenance downtime is the customer's own responsibility — Hostinger is not obligated to provide HA for a single VPS, and won't.

1. Where we actually stand today

One Hostinger VPS runs everything: Nginx, the Node app (PM2, 2 cluster instances), and Postgres — all on the same box. That box is a single point of failure end to end: if it goes down for maintenance, a kernel update, a hardware fault, or Hostinger's own network issue, the app and the database are both unreachable at the same time, for however long that takes. Nothing today survives that. Two things already work in our favor:

  • Sessions live in Postgres (connect-pg-simple), not on local disk — nothing app-specific is pinned to "this one machine's" filesystem state.
  • The company logo now lives in the database, not on local disk (this week's change) — so the only durable state that matters at all is the Postgres database itself. There is no other file-storage dependency to replicate.

That second point matters: it means "make Postgres survive an outage" is nearly the whole problem, not one part of a bigger one.

2. What "high availability" actually requires, and its cost

There is no shortcut — real HA always means the same data replicated somewhere else, and something to redirect traffic there when the primary is unreachable. The question is how automatic, how fast, and how much it costs. Three honest tiers, from cheapest to strongest:

Tier 0 — Planned-downtime discipline (what we effectively have now)

Accept the outage, but control it: a maintenance banner, a status page, doing it in your lowest-traffic window, a fresh backup-db.sh run right before, and a tested rollback. This costs nothing extra and needs no new infrastructure, but a Hostinger-initiated maintenance window (not one you scheduled) can still hit you with no notice, and you have zero recovery path if the VPS simply doesn't come back (hardware failure, not just maintenance) — you'd be restoring from last night's backup onto a brand-new VPS.

Tier 1 — Warm standby (recommended starting point)

A second, cheap VPS (can be Hostinger again or a different host — spreading providers is itself a form of HA) running:

  • Postgres streaming replication — a continuously-updated read-only copy of the database, seconds behind the primary.
  • The same app code, already deployed, idle (or actually serving read traffic — see below).

When the primary goes down (planned or not): promote the standby's Postgres to primary, point Nginx/DNS at the standby, done. With DNS TTL kept low, real downtime is a few minutes of manual work, not the length of the maintenance window, and it also becomes your disaster recovery plan for a VPS that never comes back. Cost: roughly one more small VPS (~$5-15/month) plus the setup effort below. This is a well-understood, unglamorous pattern — appropriate for where the product actually is today (one paying tenant in production).

Tier 2 — True HA (automatic failover, no manual step)

A managed Postgres provider with built-in automatic failover (not self-hosted replication), the app running on 2+ VPS instances behind a load balancer with health checks, and DNS/LB routing that reacts to a failed node without a human. This is what "thousands of concurrent users" (the long-term goal already on record) eventually needs, but it is real recurring cost (commonly $50-200+/month depending on provider and DB size) and real engineering: health checks, split-brain avoidance, replication-lag-aware reads, and — specific to this app — care around the ZATCA hash-chain reservation (getNextHashChainState's per-company row lock) so a mid-failover moment can't produce a gap or a duplicate in a company's invoice chain. Worth planning for, not worth building before Tier 1 is proven and the customer base justifies it.

3. Recommendation

Build Tier 1 now (it directly answers Hostinger's notice and gives real disaster recovery, not just planned-maintenance cover), and design Tier 1 so it grows into Tier 2 later rather than being throwaway work — same replication concept, same deploy scripts, just swapped for a managed DB and a load balancer once volume justifies the cost.

3a. Correction — the standby must be full-stack, colocated, not a split database

An earlier version of this discussion considered putting the database on a managed cloud service while leaving the app on the Hostinger VPS. That was wrong for this app: app and database exchange many small, sequential queries per request (tax lookups, document numbering, the ZATCA hash-chain lock, several inserts per invoice) — today that all happens over localhost (measured: ~20-65ms per invoice save). Splitting them across two providers would put every one of those round trips on the public internet instead, multiplying, not adding once — a real regression, not a minor one.

The fix: the standby is a full clone of the stack — app AND database together, on the same box — not a database replica with nothing next to it. Redundancy comes from where the whole stack lives, never from splitting it apart. Normal traffic stays on the primary at today's speed; the standby costs nothing in latency because it isn't in the request path. On failover, the app on the standby talks to the database on the same standby box — still local, still fast. What changes is which provider is serving you, not the app-to-database distance.

Replication itself is Postgres's own built-in streaming replication — a server feature, not application code. The app never knows it's happening; the only thing that ever changes is which host SQL_HOST/TENANT_DB_HOST in app.secrets point to, flipped once during a failover. Kept asynchronous deliberately: synchronous replication would make every write on the primary wait for the cross-provider standby to confirm it, reintroducing the exact latency problem colocation just fixed. Async means a few seconds of possible lag; for a planned failover (this project's actual trigger) that's a non-issue, since the failover script waits for lag to reach zero before promoting — it only matters for a sudden, unannounced primary failure, where the last few seconds of writes could be lost.

Standby location: near Frankfurt (the current VPS's own region — a major, well-connected hub, so a same-country standby keeps replication traffic fast) on a genuinely different provider than Hostinger — Hetzner (Nuremberg/Falkenstein) or DigitalOcean's Frankfurt region are the two candidates under consideration; either gives real independence from Hostinger's own infrastructure and maintenance schedule.

Downtime to expect, honestly, at this tier (manual, human-confirmed failover — matching every other production script in this repo, which asks for confirmation rather than acting on its own):

  • Planned maintenance (this project's actual trigger): near-zero. The primary is still up when we cut over, so it's a controlled, few-minutes switch, done ahead of the window — not the length of the maintenance window itself.
  • Unplanned failure: realistically low-single-digits to ~15 minutes — time to notice, run the failover script, and for DNS to propagate (even with a low TTL, resolvers don't all update instantly).
  • Getting closer to automatic, near-zero downtime either way is Tier 2 (a load balancer with health checks, no human in the loop) — more cost and complexity, not worth building before Tier 1 is proven.

4. Tier 1 — concrete plan

  1. Provision the standby VPS. Same OS/Node/Postgres versions as production (pin them — don't drift). Run deploy/setup-server.sh there so it's provisioned identically.
  2. Set up Postgres streaming replication primary —  standby (postgresql.conf/ pg_hba.conf, a replication role, pg_basebackup to seed it). The standby stays read-only until promoted.
  3. Keep the standby's app deployed and current. Either idle (simplest — deploy alongside every production deploy, pm2 stop until needed) or actually serving read-only traffic (reports, dashboards) pointed at the replica — a nice-to-have that also proves the standby actually works, but not required for v1.
  4. erp_app_tenant and RLS on the standby: setup-rls.sh and apply-rls-policies.mjs must run there too — a promoted replica with the plain schema but no RLS policies would be a silent regression back to superuser-only access.
  5. deploy/failover.sh (written  see below): promotes the standby's database, points app.secrets at itself (still colocated), builds/starts the app there, and prints the remaining manual checklist (DNS, Nginx/Certbot on the new box, verification). Asks for confirmation before the irreversible promotion step, same guardrail as every other production script in this repo.
  6. deploy/failback.sh (written  see below): re-clones the old primary as the new standby once it's healthy again  does not attempt to reconcile its now-stale data, wipes and re-syncs from whichever box is currently primary.
  7. DNS: lower the A record TTL for warraq.compbrain.io well before the maintenance date so a flip actually propagates in minutes.
  8. Rehearse it at least once against a scratch copy before relying on it for the real maintenance window — a failover script that has never actually been run is not a plan.
  9. Monitoring: a simple external uptime check (a free service is enough at this stage) so a real unplanned outage is caught even if no one is watching Hostinger's status page.

5. What I need from you to schedule this

  1. When is the maintenance window, and how much notice/downtime has Hostinger given? This sets how much of the above must be ready before that date versus can follow after.
  2. Budget for a second VPS (Tier 1) — same host or a different provider (I'd lean different provider, for real independence from a single company's infrastructure).
  3. Acceptable downtime/data loss if the primary vanished entirely right now, no warning — this is the number ("RTO/RPO") that actually decides whether Tier 1 is enough or you want to fund Tier 2 sooner.

I haven't provisioned anything or touched the production server for this — tell me which tier to build and I'll start with the standby setup and the replication config.

Status: proposal, nothing built yet. Written 2026-09-20 against the current codebase. Focus, as requested: (1) reporting / data processing, (2) easier data entry and validation, (3) scenarios that can be configured, not hard-coded. Worked scenarios: ZATCA rejection analysis, sales trends, WhatsApp message → quotation.

1. Principles (the rules every feature follows)

  1. The AI never touches the database. The VPS calls the AI provider outward. The model can only ask our server to run a named, read-only "tool"; our server runs it (as the logged-in user, for their company only) and sends back a small result. No credentials, no inbound access, no model-written SQL.
  2. Drafts, never postings. Anything that would create or change a document (quotation, expense, GRN) is created as a Draft marked "AI-created", and a person approves it. Nothing is posted, filed with ZATCA, or sent to a customer automatically.
  3. Rules first, AI second. Validation that can be done with code (VAT arithmetic, duplicates, open-month dates, unit mismatches) is done with code. The AI explains, suggests, and handles messy input (photos, chat text).
  4. Reuse what exists. Every reporting answer comes from the existing server-side report functions in server/lib/financialReports.ts (company-scoped, uncapped, permission-gated). No second copy of business math.
  5. Metered and capped from day one. Every call is counted against the company's plan; a spending cap exists at the provider as a safety net.
  6. Provider-neutral. A thin adapter, so a feature can move to another model by changing a setting.
  7. Small payloads. Send aggregates and the few columns needed; never phone numbers, emails or VAT numbers unless the scenario truly needs them.

5. The scenarios you asked about

5.1 ZATCA rejected invoice analysis (read-only)

  • Trigger: "Why was this rejected?" button on an invoice with status REJECTED/ERROR; also "Analyse this week's rejections" from the ZATCA screen.
  • Data: the invoice's stored zatcaValidationResults (error codes/messages) — the only thing sent. No customer contact data.
  • Grounding: a curated ZATCA error-code knowledge file (code → plain meaning → where to fix it in this app). The model must cite the code; unknown codes are reported as "unrecognised" rather than guessed. Built once from ZATCA's published rules and the errors we have already seen (see docs/zatca/).
  • Output: cause in plain language (en/ar/ur), exact field/screen to correct, and — for batches — rejections grouped by cause with counts ("7 invoices: missing buyer VAT number").
  • Guardrails: never resubmits, edits, or cancels. The existing rule stands: a cleared/reported invoice is only reversed by a Credit Note.
  • Success test: for a fixed set of real rejections, the explanation names the right code and the right fix ≥ 90% of the time.

5.2 Sales trends (read-only, also scheduled)

  • Trigger: "Ask", a "Explain this" button on the Dashboard/Sales Reports, and a weekly/daily brief (WhatsApp/email) per company.
  • Flow: sales_trend for this vs previous period, by item/customer/branch → the model writes the story (growth, top movers, customers who stopped buying, seasonality) and returns a chart spec the existing Recharts UI renders.
  • Numbers are never invented: every figure in the text must come from a tool result; the gateway checks the answer's numbers against the returned data and rejects mismatches.
  • Extras: slow/dead stock, "who is late paying" (from outstanding_receivables), reorder suggestions from the stock ledger.

5.3 WhatsApp message → quotation draft (creates a draft)

  • Channel: WhatsApp Business Cloud API webhook → POST /api/public/whatsapp/:channelId (signature-verified). Each company registers its number; a sender's phone is matched to a customer.
  • Understands: text, voice notes (transcribed), and photos of handwritten lists. Arabic/Urdu/English, and packaging words ("outer", "carton", "dozen") mapped to the product's packaging units.
  • Steps: extract lines (item, qty, unit, price if stated) → find_customer / find_product (fuzzy match, SKU, barcode) → product_price → create a Draft quotation (status Draft, source whatsapp, link to the original message).
  • Ambiguity handling: unresolved items are kept as flagged lines ("could not match: 'كرتون زيت'"), not guessed; an optional clarifying reply asks the customer ("Which size: 1L or 5L?").
  • Review: the salesperson gets an in-app notification and sees the draft in the AI Drafts inbox with the original message beside it (confidence per line), then edits/approves/rejects. Only after approval can it be sent to the customer. A configurable auto-reply ("Received, we'll send your quotation shortly") is the only thing sent automatically.
  • Safety: unknown senders create no data (they get a generic reply); per-sender rate limit; message bodies stored only as long as the draft exists (configurable).
