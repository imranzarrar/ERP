# Single Source of Truth (this ERP)

## The incident this exists for

While adding printed-address labels ("Building Number", "District", "Postal Code", "Saudi Arabia") to Invoice/Quotation printing, a key was added to `SEED_TRANSLATIONS` in `src/dbStore.ts` — the app-wide translation dictionary every other screen reads via `useTranslation()`. The printed invoice kept showing the raw English key anyway. The real lookup for Invoice/Quotation printing went through a **second, independent hardcoded dictionary** — `TRANSLATIONS` / `URDU_TRANSLATIONS` in `src/components/DocumentRenderer.tsx` — with 58 of its own key/value pairs, most already duplicating (sometimes with slightly different wording) what `SEED_TRANSLATIONS` already held. The two were resolved by two unrelated languages axes too: `SEED_TRANSLATIONS` follows the *viewing user's* UI language, the DocumentRenderer dictionary followed the *print template's* configured language — a real, load-bearing distinction, but nothing forced them to also carry separate copies of the same word list to get there.

Fixed by: migrating every key from the local dictionary into `SEED_TRANSLATIONS` (checking each one for an existing entry with a *different* value first — one word, `'Description'`, genuinely differed and the shared value now wins), then making `DocumentRenderer.tsx`'s `t()` call the same `useTranslation(db, langOverride)` hook as everywhere else, just passing the print template's language as the override instead of letting it default to the viewer's. Same underlying data, two different `langOverride` callers — not two dictionaries.

## What to do before adding new "reference data" anywhere in this app

1. **Grep for the literal string/key first**, in more than one place if the feature touches more than one rendering path. For translation keys specifically: check both `SEED_TRANSLATIONS` in `src/dbStore.ts` (the general app, keyed to `db.currentUser.uiLanguage`) **and** the `useTranslation` call sites in `src/components/DocumentRenderer.tsx` (Invoice/Quotation printing, keyed to the print template's own `language` field) — these are the two real translation axes in this codebase, and a string used in both places needs to exist in the one shared dictionary, not be added to a print-local copy.
2. **If you find an existing entry with a different value than the one you're about to add**, stop and reconcile deliberately (ask the user if the difference is meaningful, e.g. a deliberately more/less verbose printed-document wording) rather than silently overwriting or silently leaving two versions to drift.
3. **If no dictionary/constant exists yet and you're tempted to define a new one**, check whether the data genuinely needs a new axis (a real second dimension, like "language the viewer prefers" vs. "language the document is written in" were) or whether it's actually the same concept as something already in the codebase under a different name. Only add a second source when the axis is real — document why in a comment the way the templateLang distinction is documented in `DocumentRenderer.tsx`.
4. **When you do find and fix a real duplicate**, prefer deleting the redundant copy over leaving both (even "for safety") — a second copy that's merely unused today is exactly the trap that caused this incident once already; it doesn't stay unused forever.
5. This applies beyond translations — the same principle governs any place this codebase keeps a canonical list, default set, or lookup table (e.g. `DOCUMENT_TYPE_REGISTRY` in `server/lib/documentNumbering.ts`, `PERMISSION_MODULES` in `src/permissionSchema.ts`). Before adding a new hardcoded map anywhere, search for whether one already exists for that concept.
